# 团队分工（多 Agent = 多上下文）

多 Agent 的目的不是「模拟多人聊天」，而是把复杂项目拆成**独立上下文**，
每个角色只拿自己需要的信息，通过**结构化交付物**衔接。

## 角色表

| 角色 | 职责 | 输入 | 输出 | 权限 |
|---|---|---|---|---|
| **Producer / Tech Lead** | 需求裁决、阶段推进、任务拆分、决策管理 | 用户指令、`requirements.md` | 里程碑定义、`decisions.md` 条目 | 可改 `decisions.md` / `tasks.md` |
| **Researcher** | 竞品、市场、技术调研 | 调研任务 | 研究文档、结论摘要 | 只写研究文档 |
| **Game Designer** | 系统规则落地（技能 / 模块 / 道具 / 地图 / 数值） | `requirements.md` | `docs/systems/*` | 规则需用户确认后落盘 |
| **Asset Curator** | 素材盘点、缺口、授权、归一化 | 设计需求、素材库 | `docs/assets/*` | 不得把未授权素材放进生产路径 |
| **UI Designer** | 竖屏 UI 规格、原型、Pattern、Tokens | 需求 + 参考案例 | `docs/ui/*`、HTML 原型、截图 | UI 冻结需用户确认 |
| **Builder** | 实现代码与场景 | 已冻结规格 | 代码、可运行产物 | 同任务唯一 Builder |
| **Verifier** | 单元 / 集成 / 场景 / 视觉验证 | 实现产物 | 测试报告 + 截图 + seed | 只读代码，不改实现 |
| **UI Critic** | 按清单评审 UI 是否达标 | 截图 + 清单 | Critic 报告 | 只出结论 |

## 升级规则（必须交回用户）

1. 需求冲突 / 规则矛盾无法自行裁决；
2. 需要引入新素材、新依赖、新引擎；
3. 重大玩法或 UI 规格变化；
4. 同一问题 3 次尝试仍失败（长时间卡死）；
5. 发布相关动作。
