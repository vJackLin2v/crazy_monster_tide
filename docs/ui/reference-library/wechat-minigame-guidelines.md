# 参考案例 ③：微信小游戏官方设计指南（平台权威）

> 来源：微信开放文档 / 微信开放社区《Weixin Mini Game Design Guidelines》及官方转载梳理
> （检索 2026-10-12；官方页面为 JS 渲染，正文以搜索摘要 + 社区转载为证）。
> 证据等级：**规范级**（平台硬约束，不是审美偏好）。
> 与前两个参考的分工：Möbelmon = 视觉、Brotato = 结构，**本案例 = 平台约束红线**。

---

## 1. 官方给的三条硬数值

| # | 官方建议 | 本工程取值 | 是否对齐 |
|---|---|---|---|
| 1 | 设计稿基准 **750 x 1334**（4.7 寸，因大部分用户屏幕为 16:9） | **360 x 640** | ✅ **正好 0.48 倍**（750x0.48=360，1334x0.48=640.3≈640） |
| 2 | 安全区：顶部状态栏 **44px**、底部 **34px**（750 基准下） | `env(safe-area-inset-top/bottom)` + 顶部预留 >=24dp | ✅ 对齐（0.48 倍后约 21/16px，用 env 动态取值更稳） |
| 3 | 最小点击区域 **44 x 44 px** | 主按钮 >=44dp；卡片整卡可点；战斗内图标 >=32dp | ✅ 对齐（战斗内图标是特例，见 §3） |

> 第 1 条是本次最有价值的发现：**我们的逻辑分辨率不是随手定的，而是官方基准的 0.48 倍**，
> 与 750x1334 完全同比例（1:1.778 vs 1:1.779）。这点此前只是"看起来合理"，现在有权威依据。

---

## 2. 官方强调的设计原则（对我们的约束）

| 原则 | 官方表述要点 | 本工程落地 |
|---|---|---|
| 流程清晰 | 页面之间可自由切换，逻辑关系简单，无阻碍 | 主界面 → 角色选择 → 战斗 → 商店 → 战斗…；任何模态都有明确出口 |
| 单手可玩 | 小游戏以碎片时间、单手操作为主 | 动态摇杆（触点落下处生成）+ 主要交互在屏幕下半部 |
| 轻量即点即玩 | 不做重度前置流程 | 启动即主界面，2 步内进战斗 |
| 尺寸适配 | 关注不同设备的屏幕比例与安全区 | fitWidth + env(safe-area-inset-*) + 三档视口验证 |

---

## 3. 本工程的两处**有意偏离**（需要记录在案）

| # | 偏离 | 理由 | 风险控制 |
|---|---|---|---|
| 1 | 战斗内图标（暂停键）30x30dp < 官方 44dp | 战斗可视区寸土寸金，44dp 会明显挤压怪潮视野 | 放在右上角**固定位置**（肌肉记忆）、留足留白、有按下反馈；如真机反馈难按，再提升到 36~40dp |
| 2 | 逻辑分辨率 360x640 而非直接 750x1334 | 像素风 + 360 宽更贴近小游戏主流视觉密度，且像素素材以 1/2 倍渲染更干净 | 严格保持与官方基准同比例（0.48x），适配换算无损失 |

---

## 4. 对 UI 冻结的意义

1. **平台红线已核**：安全区、热区、比例三项均有官方依据，不再依赖主观判断。
2. **冻结可以落地**：Cocos 侧实现时，"逻辑分辨率 360x640 + fitWidth + Nearest" 是**有出处的要求**，
   不是某个 Agent 的偏好。
3. 后续新增任何 UI，必须回头核对本文件 §1 的三条数值。
