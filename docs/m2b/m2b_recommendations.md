# M2-B 改进建议

> 只提方案，不改数值。所有“修改”均需用户批准后另开任务。

## P0：明确的代码/逻辑错误

### P0-1 修复 pulse 技能命中窗（M2B-001）

- **为什么值得改**：源码路径确定：pulse 在 `updateAreas` 第一次更新就 `done`，此时半径≈0，导致震荡波/霜爆/荆棘环/寒冰环 4 个技能基本打不中。run_001 `frostring` 41 次释放、0 命中。
- **修改什么**：只改命中时机与去重，不改伤害/范围/冷却：
  1. pulse 不在第一帧判定；在扩散到最大半径（或明确的有效判定半径）时结算；
  2. 每个 pulse 对每个敌人最多命中一次（可用 Set 或 doneAtEnd）；
  3. 保持现有 `spawnArea` 的视觉扩散。
- **预期改善**：4 个 pulse 技能从“几乎无效”恢复为可用；早期清怪/生存数据才有意义。
- **副作用**：修复后前期难度会下降；这是行为修正不是平衡调整。必须单独版本记录，避免和历史数据混用。
- **如何验收**：
  - 单元/受控测试：敌人在 40px 外，释放寒冰环，扩散到最大半径时应命中 1 次；不得重复命中。
  - 浏览器冒烟：固定无模块、固定角色，记录 frostring 至少 1 hit。
  - 回归：530 PASS 不得下降；其余技能不变。

## P1：值得设计实验的问题

### P1-1 法师冷却缩减文案按角色修正（M2B-002）

- **为什么**：当前 `ModuleText` 对 rapid 显示 -18.5%（Lv.2），法师实际约 -22.6%，误导构筑。
- **修改什么**：详情文案接收当前 stats（或明确“基础值”+角色修正说明）；普通角色保持现显示。
- **预期**：法师玩家看到真实冷却收益。
- **副作用**：UI 文案区域变长；需保持已修好的换行高度。
- **验收**：单测普通/法师 Lv.1/2/3 数值与 `SkillCalc` 一致。

### P1-2 商店模块按当前技能兼容性提示/过滤（M2B-003）

- **为什么**：modPool 不检查 `requires`，玩家可能买到当前装不上的模块。
- **修改什么**：两种候选：
  A. 只展示至少有一个当前技能兼容的模块；
  B. 保留展示但加“需要：投射物/范围…”标签。
- **预期**：减少无效购买，提升决策清晰度。
- **副作用**：过滤会降低模块出现率；标签占 UI。
- **验收**：固定 4 技能组合/固定种子，分别检查“可兼容/不可兼容”货架；购买后安装路径不报错。

### P1-3 lifesteal 上限的受控实验（M2B-006）

- **为什么**：1843 触发只换来 1191.4 治疗，5 HP/s 硬上限可能让高攻速/高吸血投入收益不透明。
- **修改什么**：先不改规则；用固定伤害、固定攻速、不同 lifesteal 值模拟 10 秒治疗，测有效治疗/EHP。
- **预期**：确认是“上限压制”还是“伤害基数小”，再决定展示或规则。
- **副作用**：任何 cap 改动都会影响难度与吸血道具价值。
- **验收**：模拟表 + 至少 3 组对照；与现有 530 测试不冲突。

### P1-4 技能定位对照矩阵（M2B-007）

- **为什么**：7 个 projectile 技能可能重叠，但 5 局样本无法比较。
- **修改什么**：不做数值改动；建立同角色、同属性、无模块的单体/多目标 DPS/命中稳定性表。
- **预期**：确认哪些技能真正同质，再决定差异化方向。
- **副作用**：若后续改技能，会直接改平衡，需单独批准。
- **验收**：固定假人、固定距离、固定时间；每技能至少 3 次重复。

### P1-5 商店 0% 商品的固定金币实验（M2B-008）

- **为什么**：overload 12/0、orbit/frost/thornmail 3/0 样本小且没有失败购买记录。
- **修改什么**：不改价格；用固定金币、固定货架、固定种子，记录“买得起时是否买”。
- **预期**：区分价格/效果/槽位竞争。
- **副作用**：无游戏改动。
- **验收**：对 overload、rapid、harvest 做对照；结果写入实验记录。

### P1-6 multi 连续发射验证（M2B-011）

- **为什么**：0818ae9 改了发射时序，尚无独立断言。
- **修改什么**：不修改玩法；加受控测试断言 0ms 只有 1 发、0.08s 后第 2 发、方向一致。
- **预期**：确认“连续”与“分裂”区分成立。
- **副作用**：若实现有误需修实现，不调数值。
- **验收**：固定方向/无敌人/有敌人两种场景；弹体计数与时间戳。

### P1-7 难度/BOSS 的确定性模拟（M2B-010）

- **为什么**：5 局全 normal 全 death，不能判断难度跳变。
- **修改什么**：不改数值；用固定种子、固定构筑，输出每波敌人 HP/伤害/数量、BOSS 波、玩家 DPS/有效生命。
- **预期**：找出候选断层，而不是宣称已平衡。
- **副作用**：模拟不等于真人体验。
- **验收**：生成 1~20 波表格；人工只做少量复核。

## P2：体验与数据可读性

### P2-1 heal1 与每波回满的设计决策（M2B-009）

- **为什么**：每波回满使 +30 HP 的 heal1 价值偏低，heal2 已移除。
- **修改什么**：先决策：保留/移出池/改为战斗中即时价值；不要直接改数值。
- **预期**：减少“看到但没理由买”的货位。
- **副作用**：影响普通道具池数量与掉落。
- **验收**：用户批准后再做；固定金币购买实验。

### P2-2 遥测区分 item_heal / stat_heal / module_heal（M2B-005）

- **为什么**：lifesteal/killheal 被写成 module，黑科技统计被污染。
- **修改什么**：新增来源字段或事件类型；保留旧字段兼容；不改玩法。
- **预期**：模块贡献与道具贡献可分开分析。
- **副作用**：Schema 版本与历史数据。
- **验收**：旧记录可读；新记录 lifesteal 不再出现在 module 表，或明确标记为 stat。

### P2-3 商店失败购买/金币不足遥测（M2B-004）

- **为什么**：当前购买率无法区分偏好与买不起。
- **修改什么**：记录 attempt、失败原因、购买前金币；成功购买保持原事件。
- **预期**：后续商店分析可信。
- **副作用**：事件量增加；需限流。
- **验收**：固定金币/固定货架的自动化测试。

### P2-4 报告与导入格式说明（M2B-012）

- **为什么**：粘贴导入的长局只保留事件环尾部，容易被误读。
- **修改什么**：报告固定注明事件完整性；导入文件保留 `missingFields`；不补造事件。
- **预期**：读者不会把缺失事件当行为缺失。
- **副作用**：无。
- **验收**：完整性报告与 summary 一致。
