## 详细条目

### M2B-001 pulse 技能命中窗

- **系统**：技能
- **问题描述**：pulse 区域在 `updateAreas` 的第一次更新就把 `a.done = true`，而这次更新时 `a.r` 刚从 0 开始增长。只要敌人不在出生点极小半径内，后续扩散到最大范围时不再判定命中。
- **证据等级**：A（代码必然路径）+ C（run_001 frostring 41 释放、0 命中、0 伤害；shockwave/frostnova/thorn 本轮无样本）
- **数据证据**：run_001 `frostring` castCount=41、hitCount=0、damageTotal=0、killCount=0；run_001 同时有 `charge_pulse` 1/0（charge 不是 pulse，不能据此判定 charge 也坏）。
- **代码证据**：`cocos/assets/scripts/battle/Battle.ts` `fireSkill` pulse 分支 `spawnArea(..., 'pulse', ...)`；`updateAreas` 2530-2540 行：`a.r = maxR * min(1, a.t / a.life)` 后立即遍历敌人并 `a.done = true`。`spawnArea` 对 pulse 初始 `r=0`。
- **影响**：震荡波/霜爆/荆棘环/寒冰环 4 个技能在实际游戏中基本无法命中；会直接压低早期清怪与生存，并污染所有技能对比数据。
- **置信度**：高
- **建议**：P0 逻辑修复；pulse 在扩散到最大范围（或到达预先定义的有效半径）时判定一次，且每个敌人每个 pulse 只命中一次；补受控测试。
- **风险**：修复后 4 个技能从“几乎无效”变为正常，可能明显改变前期难度；必须单独验收，不与数值调整混在一起。
- **是否涉及数值**：否（命中时序/判定）

### M2B-002 法师冷却缩减文案不一致

- **系统**：UI / 黑科技
- **问题描述**：`ModuleText.moduleDetailText` 对 rapid 使用 `1 - 0.88^e`，未乘法师 `modCdrMul=1.25`；`SkillCalc` 实际使用 `0.88^(modCdrMul*rapid)`。Lv.2 文案 -18.5%，法师实际约 -22.6%。
- **证据等级**：A
- **代码证据**：`game/ModuleText.ts` rapid 分支；`game/SkillCalc.ts` 125-128 行；`data/Chars.ts` mage `modCdrMul:1.25`。
- **数据证据**：本轮无 mage 的 rapid 等级与冷却实测；不依赖样本即可确认文案公式错误。
- **影响**：法师玩家按文案低估冷却缩减，构筑决策被误导。
- **置信度**：高
- **建议**：P1 UI 修正；显示当前角色实际值（或明确“基础值”并列出角色修正），并补 mage/normal 两套断言。
- **风险**：只改显示，不影响战斗；若把“基础值”写成角色实际值，需统一所有角色。
- **是否涉及数值**：否（仅显示）

### M2B-003 商店模块与当前技能不兼容

- **系统**：商店 / 黑科技
- **问题描述**：`makeShopItem` 的 modPool 只检查 `totalMods < max` 与 used，不检查当前技能的 `requires`；`isCompatible` 只在安装时使用。玩家可能买到当前技能无法安装的模块。
- **证据等级**：A + C
- **代码证据**：`game/RunState.ts` 509-539 行 `makeShopItem`；安装路径 `RunState.ts` 411 行 `isCompatible` 才抛出不兼容。
- **数据证据**：summoner 以 meteor（area）开局，但商店出现并购买了 projectile-only 的 multi/snipe/fan/bounce；后续获得 spirit/orb 后才可用。其他角色也可能遇到。
- **影响**：购买决策被浪费；新手不知道“现在买了也装不上”。
- **置信度**：中高
- **建议**：P1 实验：商店过滤“当前无兼容技能”的模块，或在商品上显示“需要：投射物/范围…”；先做固定金币/固定货架的对照测试，不直接改价格。
- **风险**：过滤会减少模块出现率；显示标签需要 UI 文案空间。
- **是否涉及数值**：否（过滤/提示）

### M2B-004 缺少失败购买与金币不足数据

- **系统**：商店 / 遥测
- **问题描述**：`GameRoot` 只在 `buySlot` 成功后调用 `shopPurchase`；没有记录点击未购买、金币不足、主动跳过。商店购买率只能说明成功购买/展示，不能区分偏好与买不起。
- **证据等级**：A
- **代码证据**：`GameRoot.ts` 1236-1256 行；`RunState.buySlot` 557-587 行的失败原因未进入遥测；`TelemetryRecorder.shopPurchase` 只在成功路径。
- **数据证据**：overload 12/0 等无法判定是价格、效果还是没兴趣。
- **影响**：所有商店结论的证据上限被限制。
- **置信度**：高
- **建议**：P2 数据采集补充（下一轮 M2-B 工具，不改玩法）：`shop_attempt`/失败原因/购买前金币；或短期先在报告里明确“购买率≠偏好”。
- **风险**：新增事件需要改 Schema，须单独批准。
- **是否涉及数值**：否

### M2B-005 道具治疗被记成黑科技

- **系统**：遥测 / 黑科技
- **问题描述**：`TelemetryRecorder.playerHeal(amount, source)` 对非 regen/shop/waveclear 的 source 自动调用 `moduleHeal(source)`；Battle 把属性 lifesteal/killheal 作为 source 传入，于是产生 `lifesteal/killheal` 的 module 记录（acquireCount=0，trigger/heal 有值）。
- **证据等级**：A + B
- **代码证据**：`TelemetryRecorder.ts` `playerHeal`；`Battle.ts` `healPlayer(..., 'lifesteal'/'killheal')`。
- **数据证据**：module_metrics 中 lifesteal acquire=0、trigger=1843、heal=1191.4；killheal acquire=0、trigger=153、heal=142.9。它们不是黑科技模块，而是道具/属性来源。
- **影响**：黑科技排行榜会把道具效果算进模块贡献，结论错误。
- **置信度**：高
- **建议**：P2 数据口径修正：区分 `item_heal` / `stat_heal` 与 `module_heal`；保留旧字段兼容；不改玩法。
- **风险**：Schema 兼容与历史数据迁移。
- **是否涉及数值**：否

### M2B-006 回血硬上限与 lifesteal 投入

- **系统**：回血/生存
- **问题描述**：战斗回血被 `HEAL_HARD_CAP=5`（以及每秒预算）夹住；lifesteal 触发很频繁，但实际每次治疗约 0.65，极高攻速/多段构筑的吸血投入可能大部分被上限吃掉。
- **证据等级**：A（上限）+ B（数据）
- **代码证据**：`game/RunState.ts` `heal`；`game/HealRules.ts` `HEAL_HARD_CAP=5`；`Battle.healPlayer`。
- **数据证据**：lifesteal 1843 触发 / 1191.4 实际治疗（约 0.65/次）；monk 761.8、summoner 429.6；与高攻速构筑同时出现。
- **影响**：lifesteal 装备的边际收益不透明；玩家可能觉得“吸血没用”。
- **置信度**：中高
- **建议**：P1 设计实验：用固定伤害/攻速/生命构造，测不同 lifesteal 值的实际治疗与有效 EHP；先不改 cap，再决定是否调整展示或规则。
- **风险**：降低 cap 会削弱生存；提升 cap 会影响难度。
- **是否涉及数值**：是（若调整）；本轮仅实验

### M2B-007 projectile 技能定位重叠

- **系统**：技能
- **问题描述**：火球、冰矛、奥术、圣光、灵能、雷球、回旋刃都属 projectile，差异主要是 cd、单发伤害、追踪/穿透/回旋；在没有受控对比前，玩家可能只觉得“都是飞弹”。
- **证据等级**：D（设计观察）
- **代码证据**：`data/Skills.ts` 14-45 行；`SkillCalc.ts` 基础伤害/冷却成长。
- **数据证据**：5 局中同一角色最多 4 技能；不同角色/构筑混杂，不能比较。
- **影响**：技能选择辨识度、升级卡决策。
- **置信度**：中
- **建议**：P1 受控测试：同角色、同属性、无模块，单体/多目标 DPS、命中稳定性、清群效率；先验证是否真的重叠，再设计差异化。
- **风险**：改技能会直接改平衡；本轮不实施。
- **是否涉及数值**：待定

### M2B-008 商店 0 购买候选

- **系统**：商店
- **问题描述**：overload 12 展示 0 买；orbit/frost/thornmail 各 3 展示 0 买。样本小，且没有“看到但买不起”的记录，不能判定商品弱。

- **代码证据**：`RunState.makeShopItem` 价格公式；`Balance` itemBase 14 + 3.4×wave、modBase 18 + 5×wave；`overload` 是 +25% 伤害/-10% 范围。

- **置信度**：低
- **建议**：P1 固定金币/固定货架的购买实验；不要因为 12 次展示就改价格。
- **风险**：直接改价可能破坏经济。
- **是否涉及数值**：是（若调价）；本轮不实施

### M2B-009 heal1 与每波回满

- **系统**：道具/回血
- **问题描述**：每波开始回满使战斗中治疗道具的价值被规则稀释；heal2 已移除，heal1（+30 HP）仍在池中。
- **证据等级**：C/D
- **代码证据**：`Battle.startWave` 每波 `hp=maxhp`；`Items.ts` heal1；`RunState.heal(40,true)` 商店治疗。
- **数据证据**：5 局商店 heals=0、heal1 极少展示/购买；样本太小。
- **影响**：可能出现“看到了但没理由买”的货位。
- **置信度**：中
- **建议**：P2 设计审查：是否将 heal1 从池中移除/改为战斗中瞬时价值；需用户决定，不擅自改。
- **风险**：移除会影响普通道具池数量与掉落。
- **是否涉及数值**：是（若改）
