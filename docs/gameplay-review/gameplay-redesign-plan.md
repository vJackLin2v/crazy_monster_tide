## 0. 定位、约束与范围分类

**目标链条**：战斗获得资源 → 升级选择构筑方向 → 商店购买道具补强 → 战斗验证构筑 → 持续成长 → 后期爆发。

**硬约束**：不改需求书；不新增依赖；不动用户 16 个未提交文件；不提高所有伤害/经验倍率制造爽感；不重写战斗系统；20 波保持不变；复用现有架构与配置表。

| 类别 | 内容 | 本轮状态 |
|---|---|---|
| **A 类（已确认，允许实施）** | ①一只怪掉多颗经验球 ②掉落/吸收反馈优化 ③升级三选一只出属性和黑科技 ④商店只出售道具 ⑤直接相关的经验、经济、测试平衡 | 方案已给出（§2~§6）；**实施待 D-01~D-04 裁决 + 用户「继续」** |
| **B 类（只给建议，不擅自实施）** | 技能质变/进化、技能×黑科技组合、怪物行为与波次节奏、五档难度重平衡、完整/快速挑战设计、首次启动流程优化、暂停与进度恢复补强 | §8 逐项给方案 / 影响 / 成本 / 收益 |
| **C 类（本轮禁止擅自新增）** | 新角色、新地图、大量新怪物、大量新技能、大量新道具、大规模美术替换、大规模 UI 重做、未经验证的新玩法系统 | 明确不做 |


## 2. A 类 · M1：经验球系统改造（详细设计）

### 2.1 设计总原则

1. **总经验严格守恒**：`Σ 每颗 v = e.exp`。`addExp(v: number)` 支持浮点，无需凑整；`waveEndMul=0.5` 仍作用在**每颗球**，减半后总和同样守恒。
2. **只在现有机制上增强**：保留 `pop` 散落、脉动、吸附 `pull`、`vacuum` 波末吸取、拾取特效、`waveEndUps` 连续升级、`addExp` while 溢出循环。
3. **一次击杀只生成一次掉落**：拆分发生在现有 `onKill` 尾部 `Battle.ts:1722-1734` 单点，不新增击杀回调，避免重复结算。

### 2.2 拆分规则（建议值，实施前按真机帧率复核）

| 来源 | exp | 颗数 n | 每颗 v | 视觉分档 | 说明 |
|---|---|---|---|---|---|
| 普通小怪（goblin/wolf/eyebat/orc/imp…） | 1 | **2** | 0.500 | 小 · 0.85 | 2 颗即可见「散开」 |
| 普通中怪（stingerbat/hyena/axolizard…） | 2 | **3** | 0.667 | 小 · 0.85 | |
| 普通大怪（succubus/basilisk/cavebrute） | 3~4 | **3** | 1.000~1.333 | 中 · 1.0 | |
| 精英 `gnollberserker` | 8 | **8** | 1.000 | 中 · 1.0 + 环形散落 | 阶段性奖励簇 |
| BOSS | 40 | **12** | 3.333 | 大 · 1.15 + 更远抛射 | 明显奖励爆发 |

- 分档依据：`ENEMIES` 表静态 exp（`Battle.ts:1027` 不随波次放大）。
- 通用公式：`n = clamp(MIN_SHARD, ceil(exp / SHARD_UNIT), MAX_SHARD)`，`v_i = exp / n`；上表为该公式的具象化，**最终参数写入 `Balance.exp`（新增 `shards` 分组），不硬编码在 Battle**。
- **不因球数增加提高任何经验倍率**，`exp.base / perLevel / waveEndMul` 保持不动（除非 D-04 获批）。

### 2.3 对象池与生命周期（关键）

```
acquireGem(): Gem
  ├─ 池非空 → 取出，node.active = true，复位 x/y/v/pop/vx/vy/base
  └─ 池空且 active < HARD_CAP → mkSpriteNode('gem', layerArea, 12, 12) 新建
releaseGem(g):        // 拾取 / 波次清理 / 战斗结束统一走这里
  ├─ g.node.active = false（不 destroy，保留 FrameAnim 与 clips）
  ├─ 复位字段，入池（池上限 HARD_CAP）
  └─ g.node = null 化处理，避免 compact 误判
```

- 替换点：`Battle.ts:1725`（新建）、`:2680`（`destroy()`）、`:521-522` / `:2753`（`kill(g.node)`）。
- 复用时**必须重置** `node.setScale / setPosition / FrameAnim clips`，否则会出现继承上一颗球的尺寸与动画帧。
- `clearSkillRuntime()` / `resetRunState()` 改为 `releaseGem`，保证跨局不泄漏；与现有 `hitSetPool` 风格一致。

### 2.4 超量策略（不丢经验）

- `HARD_CAP = 256` 活跃球（可由 `Balance.exp` 配置）。
- 生成时若 `active >= HARD_CAP`：**合并压缩** —— 取同区域最老的 K 颗，把它们的 `v` 累加到 1 颗「聚合球」（`base` 调大、颜色/大小区分）、其余 `releaseGem` 回池。**只合并，不删除经验**。
- 拾取范围内多颗同帧命中时：**批量结算** —— 先累加 `total = Σ gain`，再调用一次 `rs.addExp(total)`，音效/特效按「每 N 颗或每 0.08s」节流一次，避免 30 颗球同帧播 30 次 `Sfx + addVfx`。
- 拾取半径保持 `st.pickup`（当前 56），不因球数增加而放大；这样「多球散落 + 需要走近连吸」的循环仍然成立。

### 2.5 波末正确性（必须修，不只是体验）

当前 `Battle.ts:1854`：`settled = gems.length === 0 || waveEndT > 3.2`，超时会直接结束波次并销毁剩余球 → **多球后可能吞经验**。M1 改为：

1. 波末 `vacuum` 一开始就生效，把 `speed` 按活跃球数动态上调（球越多吸得越快），保证 `3.2s` 内吸完；
2. 超时兜底改为「**把剩余球按当前规则全部结算入账**（仍乘 `waveEndMul`），再 `releaseGem`」，绝不静默丢弃；
3. 结算完成后才置 `waveAbsorbDone` → `onLevelUp(waveEndUps)` → `finishWave()`，保持现有升级连续触发与经验溢出逻辑不变。

### 2.6 性能预算与验收

| 项 | 预算 / 验收线 | 依据 |
|---|---|---|
| 活跃球节点 | ≤ 256，超出走合并 | 第 16 波公式推算约 27.6 颗/秒新增（理想上界） |
| 池复用 | 连续 3 波后 `mkSpriteNode('gem')` 新建次数趋近 0 | 对象池有效性 |
| 总经验 | 同一怪拆分前后 `Σv` 完全相等；全额拾取与波末减半两条路径分别核对 | 守恒约束 |
| 重复结算 | 同一死亡事件只生成一次掉落；`addKill` 仍不结算经验 | `RunState.ts:174-189` |
| 升级 | 经验条、连续升级、`exp` 溢出、波末攒卡全部与改造前一致 | `Battle.ts:2838-2858` |
| 无残留 | 波末 / 换局 / 阵亡 / 结算后 `gems.length === 0`，池内节点 `active=false` | 节点生命周期 |
| 真机 | 微信小游戏真机帧率与内存需实测（当前无证据，不写「通过」） | 基线缺口 |

## 3. A 类 · M2：升级三选一与商店职责分离

### 3.1 目标规则

- **升级三选一**：只出「属性成长」与「黑科技/机制」；**不再出现道具**（`item` 权重归零）。
- **商店**：只出售道具；**不再出现 `module` / `heal` / `attr` 非道具类型**。
- **金币、刷新、锁定、跨波携带、购买生效、存档/结算/角色配置**：全部保持现有实现。

### 3.2 ⚠️ D-01：必须先裁决的架构冲突

> 角色开局只有 1 个技能（`Chars.ts`），`ShopSlot` 无技能类型，`rollRewards()` 的 `skill/skillup` 是**获得第 2~4 个技能与强化技能的唯一途径**。严格两类会直接破坏 4 技能 × 3 槽构筑。

| 方案 | 升级池 | 技能获取 | 改动面 | 评价 |
|---|---|---|---|---|
| **P-A 严格字面** | `attr + module` | **断供**（需另建获取渠道） | 需新增系统（C 类禁止）、改 `Chars` / 存档 / 结算 / UI | ❌ 本轮不可行 |
| **P-B 推荐** | `attr + 机制类(module + skill/skillup)` | **保留**，与黑科技同池 | 仅 `Balance.reward` 权重 + `rollRewards()` 的 `item` 分支 + UI 标签合并 | ✅ 达成「升级不出道具、商店不出黑科技」的职责分离，不破坏构筑 |
| **P-C 折中** | `attr + module`，技能改为波次里程碑固定解锁（第 4/8/12 波各 +1） | 保留但变成确定性 | 新增波次→技能规则，需回归全部升级/存档测试 | ⚠️ 属新规则，需单独批准 |

**本方案默认按 P-B 编制**，但**实施前必须请用户明确**：「技能获取/强化是否算作『黑科技/机制类』」。若用户坚持字面两类，则 M2 暂停，先走 P-C 或另开里程碑，不强行实施。

### 3.3 候选池保障（防空池 / 不足三张）

- 内容量：`ATTRS 24`、`MODULES 17`（每技能 3 槽、`requires` 兼容、`max` 上限）、`SKILLS 17`（最多持 4）、`skillup` 可重复 → 三类相加足够生成 3 张。
- `rollRewards()` 现有 `used` Set 只保证**同一轮三张不重复**（`RunState.ts:226, 282-285`），保留。
- 保留现有保底：`RunState.ts:243-244`「第三张仍是属性且前两张都是属性 → 改抽机制类」。
- **新增兜底**（P-B）：若 `module` 池因 `max`/兼容全空 → 退回 `skill/skillup`；若两者皆空 → 用**可重复属性**补位，仍保证返回 3 张，绝不返回空数组（现有 `while (out.length<3 && guard++<200)` 已有限制，需保证 guard 用尽也不返回 <3）。
- UI：`Modals.ts:42` 的 `kind` 标签把 `skill/skillup/module` 统一归到「机制」色系说明，避免玩家看到「5 类」；**不改布局，不改热区**。

### 3.4 商店改造与兜底（D-02 / D-03）

- `makeShopItem()`（`RunState.ts:509-539`）删除 `modPool` 与 `modPrice()` 分支，4 个货位全部从 `ITEMS` 抽；`ShopSlot.kind` 收敛为 `'item'`（或保留字段但只写 `'item'`，避免改存档结构）。
- **D-02 兜底**：把现有 `heal` / `attr` 两个兜底**道具化**——新增 2 个 tier1 道具定义（如「急救包」「属性锦囊」），走 `ITEMS[s.id].apply()`；`GameRoot.ts:1284-1287` 的 `heal` 遥测分支改为按道具 id 处理。这样「商店只出售道具」字面成立，且不新建系统。
- **D-03 池枯竭**：20 波 × 4 = 80 货位 > 79 件唯一道具。二选一：
  - ①允许已持有的普通道具重入池并可叠加（改 `itemAllowedInPool`，`rs.items` 本就允许重复、`GameRoot.ts:1308-1310` 已按 id 统计数量）→ 改动最小；
  - ②保持唯一，池空时统一用兜底道具填满 4 个货位。
  推荐 ①+② 组合，并在 `Balance.shop` 增加可配置开关。
- 金币/刷新/锁定/购买生效逻辑**一律不动**：`rerollCost()`、`rerollShop()`、`buySlot()` 的「先校验再扣钱」（`RunState.ts:561-569`）保持不变，防止重复扣费。

### 3.5 改造前后经济对比（公式推算，非玩家数据）

| 指标 | 改造前 | 改造后（P-B） | 判断 |
|---|---|---|---|
| 每波金币收入 | 第 1 波约 50，第 20 波约 1102，20 波累计约 9442（理想上界） | **不变** | 不调倍率 |
| 升级池 item 权重 | 0.25 / 0.25 / 0.30 | **0** | 每 100 次升级少 25~30 件免费道具 |
| 商店每波道具位 | 约 2 个（50% 抽 item） | **4 个** | 道具供给翻倍 |
| 20 波道具位 | 约 40 | 80 | 需 D-03 兜底 |
| 商店模块位 | 约 2 个 | **0** | 黑科技只能从升级拿，构筑方向更清晰 |
| 买得起吗 | 均价 ~50 金 / 件 | 全买 80 件约 4000 金 ≪ 9442 | ✅ **买得起，且金币仍溢出** |
| 成长会不会变慢 | 道具部分免费 | 道具全部付费 | 会略慢，但金币过剩可覆盖；**不得靠提高经验/伤害倍率补偿** |
| 五档难度经济 | `goldMul 1.20→0.78`、`shopPriceMul 0.90→1.35` | 结构不变，仅商品构成变化 | 地狱档 `goldMul 0.78 × shopPriceMul 1.35` 压力最大，M3 必须单独验 |

> 结论：职责分离**不会造成「买不起」**，主要风险转移到「升级池种类变少 → 三张卡更像」和「后期空货位」，由 §3.3 / §3.4 的兜底覆盖。

## 5. 经验成长曲线分析（不改数值，仅给依据）

| 项 | 值 | 来源 |
|---|---|---|
| 初始需求 | 5 | `RunState.ts:47` `EXP_BASE` |
| 递推 | `round(5 + lv × 3.2)` → 5, 11, 15, 18, 21, 24, 27, 31, 34, 37… | `RunState.ts:169` |
| 敌人经验 | 普通 1~4 / 精英 8 / BOSS 40，**不随波次放大** | `Enemies.ts:7-23`、`Battle.ts:1027` |

**诊断**：升级次数（69 次）远超机制类内容供给（17 模块 × max 3 + 17 技能，且技能限 4 个）→ 中后期必然大量重复属性卡。这是「升级选项没意义」的根因之一。
**本轮处理**：M1/M2 **不动经验曲线**（避免把两件事混在一起验证）；把「是否放缓曲线 / 提高 `EXP_PER_LEVEL` / 调整 `waveEndMul`」登记为 **D-04**，作为独立里程碑单独平衡 + 全量回归。

## 6. 经济系统分析（不改倍率）

见 §3.5 与 `diagnosis-report.md` §3.4。要点：金币收入随波次近似超线性增长，而商品位固定 4/波、道具唯一 79 件 → **后期金币溢出是结构问题**，不是价格问题。本轮只用「兜底 + 允许叠加」保证不出现空货位与买不起，**不擅自加消费出口**（那属新系统 / C 类）。

## 7. 前 5 分钟体验目标（验收口径，非承诺数据）

| 时间 | 目标体验 | 可观测信号 |
|---|---|---|
| 0~20s | 尽快进入战斗、看到怪潮、理解「技能自动开火」 | `session_start → run_start` 间隔；首杀时间 |
| 20~60s | 击杀 → 多球散落 → 走近连吸 → 经验条连续跳动 → 第一次升级 | 首经验 / 首升级时间；一次击杀的球数 ≥2 |
| 1~3 min | 升级三选一能明确指出方向（属性 vs 机制）；商店能买到并立刻感到变化 | 升级卡类别分布；购买后属性面板数值变化 |
| 3~5 min | 机制开始成型（至少 1 个黑科技生效），战斗压力开始变化 | 已装模块数；技能数 >1 |
