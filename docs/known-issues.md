## KI-001 怪物死亡后不会消失

| 项 | 内容 |
|---|---|
| **发现** | 2026-10-12 用户实测反馈（HTML 原型） |
| **现象** | 怪物被打死后**尸体留在原地不消失**，并且卡在死亡动画的第一帧 |
| **根因** | `updateEnemies()` 的循环体开头有 `if (e.dead) continue;`，而累加 `deathT` 的那行在它**后面** → `deathT` 永远是 0 → 移除条件 `deathT < 0.75` 永远成立 |
| **影响** | ① 视觉错误：尸体不消失；② **实体数组无限增长**（一局 20 波会残留上千个死单位）→ 内存与遍历开销持续上涨（性能隐患） |
| **为什么测试没抓到** | E2E 与门禁都只断言"能击杀"，**从未断言"死掉的单位会被移除"** |
| **修法** | 把 `if (e.dead){ e.deathT += dt; continue; }` 提到循环体最前面（在 flash/animT 更新之前） |
| **Cocos 侧要求** | 实现敌人生命周期时，**死亡状态必须先累加计时再跳过逻辑**；并写一条单测断言"死亡后 N 秒实体被回收" |
| **状态** | ✅ 原型已修（1 行）+ 已加回归断言；Cocos 侧按本条实现 |
| **回归断言** | `死亡单位会在 0.75s 内被移除（尸体不残留）` |

## KI-002 画面只有底色和数字，单位/特效全部不可见

| 项 | 内容 |
|---|---|
| **发现** | 2026-10-13 用户实机反馈（Cocos 工程） |
| **现象** | 打开 Boot.scene 预览：**只有蓝色竞技场底色 + 跳动的伤害数字**，玩家/敌人/特效一个都看不见；控制台无报错 |
| **根因** | 本工程的图片被导入成 **`texture`**（meta 里 `userData.type = "texture"`，子资源只有 `6c48a texture`），而代码加载的是 **`spriteFrame` 子资源** → `resources.load(.../spriteFrame)` 全部失败。失败被吞掉，所以**没有任何报错**，只是"少东西" |
| **为什么底色和数字还在** | 底色是 `Graphics` 画的、数字是 `Label` —— 二者不依赖图片资源 |
| **次生问题** | ① 我的 `loadSF` 静默吞掉了错误（**正是原型阶段明令禁止的"静默变透明"**）；② meta 里过滤器是 `linear`，像素风会被插值糊掉 |
| **修法** | ① 加载改成**双路**：先试 `spriteFrame`，失败则取 `texture` 子资源**现场构造 SpriteFrame**（`rect`/`originalSize` 必须设，否则尺寸为 0 不可见）；② 加载成功即强制 `NEAREST`；③ 失败必须 `console.error`（前 5 条）；④ 单位先显示**纯色兜底块**，保证"看得见" |
| **另一处同源问题** | `mkSpriteNode` 里先设 `UITransform.contentSize`、后 `addComponent(Sprite)` → Sprite 初始化时按空 spriteFrame **把尺寸重置成 0×0** → 同样不可见。已改为 **Sprite 之后再设尺寸**，并在 `FrameAnim.setClips` 加尺寸防御 |
| **状态** | ✅ 已修（代码层，不依赖编辑器） |

**教训**：症状（"什么都看不见"）和根因（资源子类型不匹配）完全不搭。
以后凡是"画面少东西但没报错"，**第一步就看资源加载统计**——
所以这次顺手在屏幕底部加了调试行：`素材 N 张 / 失败 M`。

## KI-004 战斗画面里长时间看不到怪（屏幕发空）

| 项 | 内容 |
|---|---|
| **发现方式** | 2026-10-13 读图（`390x844-3-battle.png`，开波 4 秒时的真实战斗帧） |
| **现象** | 画面里**只有主角和格子底，一只怪、一个特效都没有**；VLM 原话「画面中没有显示任何怪物」「没有明显的特效」 |
| **根因** | 生成半径 195~235 世界单位，而可视世界只有 180x320（**横向半宽仅 90**）。横向刷出的怪距离是可见半宽的 2~2.6 倍，走路速度 50 px/s → **要 2~5 秒才走进画面**；第 1 波每 1.1 秒才刷 1 只，所以开局几秒屏幕上几乎什么都没有 |
| **影响** | 观感"空"、没有"怪潮"感；和用户想要的"扑面而来"相反 |
| **可选修法** | ① 生成半径按**可视半对角线**而不是固定值（横向别放那么远）；② 开场预铺几只怪；③ 波次开始时给一小波群体刷新 |
| **状态** | 待确认（用户此前说过第 2 波太凶，所以密度调整要谨慎，不能简单调回去） |

## KI-005 【真凶】运行时设计分辨率是 1280x720，不是 360x640 → 单位只占屏高 3.6%

| 项 | 内容 |
|---|---|
| **发现方式** | 2026-10-13 用 **Playwright 连上 Cocos 预览服务（127.0.0.1:7456）** 直接查运行时状态 |
| **实测数据** | `cc.view.getDesignResolutionSize()` = **[1280, 720]**（！）<br>`cc.view.getVisibleSize()` = **[1280, 2702]**<br>`World.scale` = [3,3]（旧代码的写死值） |
| **现象** | 单位 = 32 世界单位 × 3 = 96 设计px，而可视高度是 **2702 设计px** → **占屏高 3.6%**（原型是 10%）—— 小了近 3 倍 |
| **根因** | 我写在 `settings/v2/packages/project.json` 的 `designResolution: 360x640` **没有被编辑器采用**；预览的 `settings.js` 里生成的是 `1280x720` |
| **第二个问题** | 预览跑的是**旧编译产物**（worldScale=3 是 D-30 那版代码），编辑器没有重编译我之后的改动 |
| **修法** | ① **在代码里强制设定**：`GameRoot.onLoad()` 里 `view.setDesignResolutionSize(360, 640, ResolutionPolicy.FIXED_WIDTH)` —— 不再依赖编辑器设置；<br>② 相机自适应 cover（D-31）**本身就能治这个病**：它是从 `getVisibleSize()` 反推的，设计分辨率错了也照样把单位算成屏高 10% |
| **状态** | 代码已改；**需要编辑器重编译**（切到编辑器窗口 / 预览点刷新）才能生效 |

### 新增的验证能力（重要）

**可以直接连 Cocos 预览查状态 + 截图了**：

```js
// Playwright 连 127.0.0.1:7456（Cocos 预览服务）
cc.view.getDesignResolutionSize()   // 运行时真实设计分辨率
cc.view.getVisibleSize()            // 实际可视设计尺寸
world.scale / world.position        // 相机是否按预期工作
unit.children.length                // 场上单位数
+ page.screenshot()                 // 真实画面
```

**闭环**：Playwright 截图 → 本地 VLM 读图 → 我据此判断"看起来对不对"。
以后不用再靠猜。

## KI-004 已修 + KI-006 视觉对比方法（2026-10-13）

### 修法（三处，全部"从真实可视尺寸推导"，不再写死数字）

| # | 改动 | 原因 |
|---|---|---|
| 1 | `Camera2D`：`s = max(visW/VIEW_W, visH/VIEW_H) * ZOOM_MUL` | 自适应 cover：不管屏幕/设计分辨率是什么，单位都占屏高固定比例 |
| 2 | `ZOOM_MUL = 1.15`（`Const.ts`） | 用户实测单位仅占屏高 **3.6%** 后要求"放大起码 3 倍"→ 3.6x3=10.8%，取 11.5% 留余量 |
| 3 | `spawnPointAround` 改由**可视尺寸**推导半径（半对角线 x1.02~1.22）<br>+ 开场先铺 2~5 只 | 原来写死 195~235，比整个可视区还大 → 怪走 2~5 秒才进画面，屏幕发空（KI-004） |

### 验证方法（新增，可复用）

**注入式对比**：不需要等编辑器重编译 —— Playwright 连上运行中的预览，直接改运行时状态再截图。

```
1. Playwright 连 127.0.0.1:7456（Cocos 预览）
2. 禁用 Camera2D 组件 → world.setScale(S) → world.setPosition 把玩家摆到屏幕中心
3. 截图 canvas 元素
4. PIL 把 DEMO / 现状 / 修好后 并排成一张对比图
5. 本地 VLM 读对比图（**问"哪张更大"这类相对问题，比让它估绝对值可靠得多**）
```

### 对比结论（VLM 原话）

| 问题 | 回答 |
|---|---|
| 修好后 vs DEMO，主角大小？ | **「基本接近」** ✅ |
| 修好后画面怪多吗？ | 「数量较多」 |
| 修好后 vs 现在，哪张热闹？ | 「修好后更热闹」 |
| 修好后能达到 DEMO 观感吗？ | **「能达到，但在细节和复杂度上稍有不足」** |

剩余差距：**细节 / 动态效果 / 整体氛围**（不是尺寸问题了）。

### ⚠️ 注意

以上是**注入模拟**的结果。代码已改好，但**编辑器需要重编译**（切到编辑器窗口或预览点刷新）
才能真正生效；预览一直在跑旧编译产物。

### 三个根因（全部记录在案）

1. **运行时设计分辨率是 1280x720**，不是我在 project.json 里写的 360x640

### 方法论沉淀（本次最大的收获）
